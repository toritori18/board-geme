# 振り返り報告書の出力テンプレート

読み手は**技術が分かる経営者**。技術用語はそのまま使ってよいが、技術の説明で終わらせず、必ず「それが何を意味するか」まで書く。

## 骨子

見出しは以下の4つで固定（順序も変えない）。

```markdown
# ふりかえり（<対象範囲>・<開始日>〜<終了日>）

<冒頭サマリ：3〜5行>

## 成果
## 工夫した点
## 改善したい点
## 学んだこと
```

### 冒頭サマリ（3〜5行）

読み手が最初に読む部分。ここだけで判断できるよう、以下を含める。

- 対象範囲・期間・規模（コミット数など、根拠のある数値）
- **この期間で何が前に進んだか**を1〜2文
- **判断・対応が必要な残件があるか**を1文（無ければ「無し」と明記）
- このファイルを版管理しない旨

## 各見出しの書き分け

| 見出し | 書く内容 | 避けること |
|---|---|---|
| 成果 | 利用者・サービスから見て**何ができるようになったか**。機能／データ基盤／開発基盤などの単位でまとめ、技術要素は「何を可能にしたか」に接続する | 着手しただけのものを成果に含める。実装作業の列挙で終える |
| 工夫した点 | 判断が分かれた場面での選択と根拠。**何を取り、何を捨てたか（トレードオフ）**をセットで書く | 単なる作業手順の列挙。選択肢が1つしかなかったものを工夫として書く |
| 改善したい点 | 未対応・積み残し・根拠が弱いまま暫定値の箇所。**放置した場合に何が起きるか（影響）**と、判断を仰ぐ必要があるものを明示する | 反省の言葉で終える。影響の見積もりなしに列挙だけする |
| 学んだこと | 次の意思決定・再発防止に効く知見。外部サービスの暗黙仕様やハマりどころは**再現条件**まで書く | 一般論・教科書的な記述。プロジェクト固有でない話 |

## 書き方の指針

- **結論を先に書く。** 各項目は「何が起きたか／どうなったか」から始め、経緯は必要な範囲で後述する
- 各項目は「何を」だけでなく「なぜ／どうなったか」まで書く。箇条書き1行で終わらせない
- 数値を出すときは根拠（コミット・実測日）を添える。根拠を示せない数値は書かない
- 断定できない事柄は「未確認」と明記する。推測を事実のように書かない
- コミットへのリンクは `https://github.com/toritori18/board-geme/commit/<hash>` 形式
